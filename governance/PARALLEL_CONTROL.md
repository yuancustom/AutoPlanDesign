# AutoPlanDesign｜P1–P3 三路并行开发控制总览

版本：1.0.0｜日期：2026-09-11｜性质：开发运行规程，不是业务功能完成报告  
适用：同一仓库的三个独立项目、多开发者/多 AI 会话、单一 main。首次核验基准：`69a4a99a505d997a3ed3e64126216886a2168653`。

> **一个总控、三条实施线、一套版本化合同；代码可以并行写，main 发布和同一台 16GB 机器的模型任务必须串行。**
>
> 本文件补充根 `CONTROL.md` 的并行执行规则，不替代产品总控、任务台账或实验登记。它不自动启动开发 Agent，不建立后台监控，也不把约定的登记表当作已部署的锁服务。各路每次开始、交接、提交、接口变化时都要遵循。

## 1. 总览：现在在哪里、接下来先做什么

下表是上述提交的核验快照，不是随代码自动更新的实时状态。每次开工重新读 `backlog.json`、`delivery_status.json`、项目 README、实际代码和 CI；发现描述不一致记录差异，不以聊天记忆裁定。

| 线 | 现有资产 | 尚未证明 | 首轮切片 |
|---|---|---|---|
| P1 / outline-plan | 详细设计、SVG/尺度交互原型、冻结 L 形基线 | 生产输入校准、通用布局、本机模型质量 | P1-01：闭合轮廓/尺寸证据/变换/冲突检查与真实轮廓导出 |
| P2 / region-edit | 详细设计、涂抹/候选/恢复 HTML 原型 | 生产持久化、多标签事务、局部模型重绘、几何同步 | P2-01：原图坐标和蒙版；GOV-01 通过后接 P2-02 持久化 |
| P3 / plan-delivery | 24 章开发设计、Skill 的部分 vendor 文件 | 完整 Skill 导入、重建、同源导出、BIMFACE 联调 | P3-01 当前 BLOCKED；先提出独立输入准备子任务，不调用缺失 validator |
| 总控 / 集成 | CONTROL、合同 0.1.0、台账、实验规则与 CI | 自动调度、完整端到端产品 | GOV-01 合同澄清、BENCH-01 样例/硬件登记，随后 GOV-02 |

P3 缺失项以 `projects/plan-delivery/IMPORT.json` 为准：`assets/project.schema.json`、`scripts/validate_project.py`、`scripts/validate_deliverables.py`。不能因为“要三路开工”就解除阻塞、复制改名绕过被拦截内容或宣布原套件通过。可先研究导入 UI、参数证据台账、IMAGE_ONLY 会话、错误呈现、受控 fixture 适配方案；子任务须由总控登记明确无该依赖的范围，父任务仍 BLOCKED。

## 2. 文件各管什么：避免第二套台账

| 问题 | 唯一记录位置 / 责任 |
|---|---|
| 产品目标、三项目边界、尺度/隐私/成果硬约束 | `../CONTROL.md`，总控维护 |
| 三路协作、发布、交接、升级规则 | 本文件，根 AGENTS 和各项目 AGENTS 引用 |
| 做哪些任务、依赖、状态、阻塞 | `backlog.json`，总控汇总；项目子任务须映射父 ID |
| 文档、原型、生产实现、模型、人工验收分别到哪 | `delivery_status.json`，不能合为一个百分比 |
| 谁在做、改哪些路径、谁可发布/使用机器 | `coordination.json`，总控单写；初始无认领、无锁 |
| 数据字段、单位、版本、错误与兼容规则 | `../contracts/`，总控协调生产方和消费方 |
| 每次开发的证据、未完成、下一步 | 项目 `handoffs/<session_id>.md`，模板见下 |
| 接口/技术分歧和决定 | 项目 `docs/adr/` 提案；跨项目决定在 `governance/decisions/` |
| 模型候选/预算/硬件/所有尝试 | `../benchmarks/`；子项目先保存实验提案与原始记录引用 |

README 只做导航，不另维护一个可漂移的“完成率”。Issue 可以用于讨论，但不能与 JSON 台账各写一套状态。叙述与合同冲突时停止交接、提出变更，不私自宣布其中一个失效。

## 3. 职责和写入边界

用户是产品负责人：决定范围、接受交互体验、确认建筑参数与高风险变更，授权文件外发。总控角色是协调和集成负责人，不是第四个重复开发建筑算法的团队；由用户指定的人或在用户触发时运行的管理会话承担，不假设有常驻 Agent。

| 角色 | 日常可改 | 不能自行改 |
|---|---|---|
| P1 开发 | `projects/outline-plan/` 的 src/frontend/docs/tests/preparation 等非冻结部分 | P1 baseline、P2/P3、共享合同、根 CI/台账 |
| P2 开发 | `projects/region-edit/` 的前后端、原型、文档、测试 | P1 内部模块、P3、合同枚举、根 CI/台账 |
| P3 开发 | `projects/plan-delivery/` 的非 vendor 适配、文档、测试和 viewer | 冻结 vendor/IMPORT、P1/P2、三格式口径、共享合同 |
| 总控 | 根文档、governance/contracts/benchmarks/agent/tools、根测试/依赖/CI | 不代用户审批图纸，不用管理提交伪造模型成绩 |

确需跨界的修改提交变更单，由对应责任人一起确认并登记一次跨项目任务。路径所有权是流程约定，**不是 GitHub 已配置的权限隔离或 branch protection**。

每条实施线 WIP 上限先设 1 个主任务。前端和后端可在同一切片内推进，不开启大量互相依赖却都未完成的任务。三条线应使用独立工作目录/克隆，不能三个终端同时修改同一工作树。

## 4. 开工前的最小管理动作

每次会话先完成“开工卡”，并由总控将认领写进 `coordination.json` 的 `active_claims`：

```text
session_id / actor_id / project / task_id / parent_task_id
base_main_sha / read_contract_version / read_contract_hash
allowed_paths / acceptance_cases / dependency_snapshot
started_at / heartbeat_at / expires_at / next_checkpoint
```

日期为带时区 ISO 8601。actor_id 是本次执行者/会话标识，不假装已拥有某 GitHub 用户身份。到期时间由本轮登记，不自动无限延长。超时认领先联系/回读实际状态、记录撤销再重分配；过期开发者失去发布资格，不能凭旧登记继续提交。

只有 READY 且依赖已满足的任务转 IN_PROGRESS。想在 BLOCKED 父任务下并行做独立准备，先登记子任务真实依赖、验收和排除项；不删除父阻塞，不把准备代码当作全链路实现。已有 P1 子任务与 P3-D01～D22 使用映射，不平行发明第二套 ID。

JSON 登记依赖总控单写与 Git 当前版本检查；它本身不是原子分布式互斥锁。未部署自动协调器期间，各路将开工卡交给同一个总控窗口确认；文件未确认之前只读分析，不启动冲突写入。

## 5. 一轮开发怎么走

1. **读现状并认领**：确认 main、任务、合同、范围和输入来源；不能按旧聊天从头重做或清空目录。
2. **先写验收样例**：本切片最小正常用例、失败用例和影响范围；先约定再看结果。
3. **实现一个可运行切片**：文档、代码、测试同步；结果、mock、固定图、程序几何分别标记。
4. **自测与交接**：按模板提供命令、输入/配置 hash、输出位置、未测范围、风险与下一任务。
5. **总控评审并排队发布**：确认路径、依赖、合同、证据及主分支最新变化。
6. **回读 main 与 CI**：发布后确认提交包含预期文件；CI 失败保持 REVIEW/阻塞，不因已推送而 DONE。
7. **归档与下一轮**：更新原台账和分维度状态、释放认领/设备；验收认可只绑定具体版本。

每轮交接文件不可被下一轮覆盖。命名如 `projects/region-edit/handoffs/P2-01-session-20260911-A.md`。完成提交 SHA 和发布后 CI URL 可由总控在后续管理提交补入，不把尚未存在的提交写成完成。

## 6. 只用 main 时怎样避免互相覆盖

保持用户要求：**不建功能分支或 PR，保留 main 历史，不 force push**。这要求把开发并行和发布串行分开。

发布队列条目至少含 queue_id、session_id、task_id、base_sha、变更路径、补丁/待提交内容 hash、测试证据。总控一次只给一个条目发布窗口；可由总控统一提交，或授权该条目执行者提交，不能两者同时发。

发布前重新读取 `main=S`：

- 仍等于开发基础：按白名单应用变更、跑相关检查，创建父提交为 S 的新提交。
- main 已变：比较改动，保留其他路更新，将本变更应用到最新基础；不直接用旧快照覆盖整仓。
- 相同路径/接口冲突：停止并协调，不能靠“取我这边”消除冲突。
- 用 Git API 时 `update_ref(force=false)`；被拒绝则重新读取/合并/验证，不改 force=true。它只检查历史关系，不验证语义。
- 用本机 git 时先 fetch、检查工作树并合并最新 main，测试后普通 push；拒绝即停，不 reset --hard 删除他人变更。

多文件变更应以一次提交发布，防止 main 中出现 HTML 已有而 JS 缺失、合同已升级而适配未到的半成品。GitHub 网页逐文件编辑只用于独立安全的小文档变更。

紧急回退分两类：代码通过新的 revert 提交恢复，保留历史；数据库/文件格式变更必须按迁移策略处理，不能假定回退代码会恢复数据。用户方案版本回退由 P2 创建恢复 revision，与 Git 代码回退不是同一件事。

## 7. 接口先统一，不等产品都写完才集成

跨项目只走公开接口与版本化文件协议，不跨 import 内部 Python/前端模块。每条线独立测试，合成输入须标明 SYNTHETIC / test_only，不能冒充上游真实输出。

| 边界 | 生产方要保证 | 消费方要拒绝 |
|---|---|---|
| P1 → P2 | 每层图片、几何、尺寸证据、坐标变换、revision/hash 对应 | 缺 hash、错误 floor、图像/几何不匹配、未声明尺度 |
| P2 → P3 | 接受的版本、修改语义、几何 CURRENT/STALE、审批及影响楼层 | 静默消费 STALE 旧几何、复制旧批准、未知尺度假装米制 |
| P3 → Agent | 同一 BuildingIR/revision 的 DXF/PDF/GLB、回读与未解决项 | 用贴图平板/外壳拉伸冒充完整重建，三种成果版本混用 |

**当前要先解决的两个合同议题：**

- 0.1.0 PlanRevision 要求米制变换；P2 外部未知尺度图片先用内部 ImageEditSession，不塞假矩阵。要统一未知尺度入口，由 GOV-01 评审扩展和迁移。
- P3 必须能独立接收已详细设计的图片，不依赖 P1/P2 先运行。STALE 的旧几何不可直接用；若经批准从当前图片重新识图，应建立新重建请求、保留来源、重新确认尺度/几何。这个转换通过 ADR/合同/负例落地，不能由某一项目文字单方面放行。

合同变更单使用 `templates/CONTRACT_CHANGE.md`：理由、受影响方、原/新 JSON、版本、错误码、旧数据迁移、回退、正负 fixture、生产方/消费方检查、审批证据。未经确认的提案不写成 ACCEPTED。

## 8. 用一个贯穿样例提前联调

先冻结一个**合成的、尺寸明确的三层 L 形**作为共享接口测试集；case_id、每层 outline、尺寸来源、floor/object IDs、预期输出及 hash 由 GOV-01/BENCH-01 共同登记。它不是用户原图测量结果；不可继承前文 H 形或旧 diagram_units 的尺度。

联调拆成小步，而不是等三项目全部完成：

- **I0 合同**：各路读同一 fixture，字段/坐标/拒绝条件一致，不调用模型。
- **I1 P1→P2**：P1 真正输出一层后 P2 导入、涂抹、保存未覆盖的版本链；用合成候选时明确 MOCK。
- **I2 P2→P3**：验证被拒绝候选不交付、STALE 被阻断、批准后的匹配版本可进入 P3 输入适配。vendor 阻塞未解决时只验输入门禁。
- **I3 三层几何交付**：同源生成三格式，检查尺度、层间核心、门窗开洞和回读；无模型时标 GEOMETRY_BASELINE。
- **I4 真实端到端**：真实模型三轮编辑＋拒绝＋恢复＋中断，再经审批导出；单独保存模型原始结果。

每一对接口第一次产物出现就联调。正式 Agent 可提前搭持久状态/工具桩；只有真实三路集成和异常恢复通过后，才能称完整 Agent。查看页 HTML 是应用能力，不是 P3 第四种建筑交付物。

## 9. 什么叫完成：不要把五种状态混在一起

沿用台账状态 TODO → READY → IN_PROGRESS → REVIEW → DONE；BLOCKED 保留原因/责任/解阻条件，DEFERRED 写延期决定。代码作者自测通过只能提交 REVIEW，总控做工程评审；用户体验和建筑参数批准仍要用户明确确认。

| 验收维度 | 必备证据 | 不能替代它的东西 |
|---|---|---|
| 文档 | 输入/输出/失败/非目标/接口/验收可执行 | 大段愿景或只给源码链接 |
| 原型 | 实际点击/撤销/恢复等浏览器记录和限制 | 原型可点不等于生产后端存在 |
| 实现 | 新环境运行、错误路径、持久化/合同回归、对应提交 | 固定图片、空输出、mock 成功 |
| 模型 | 实际权重/后端/输入 hash、raw、参数、耗时和设备口径 | dry-run、单元测试、别人的 GPU 成绩 |
| 用户验收 | 针对具体版本和范围的反馈证据 | Agent 自己填写 human_accepted |

技术验收底线：P1 尺度冲突不得生成假米制；P2 final 的授权区外像素差=0，raw 泄漏另测；P3 STALE/未知尺度不能导出假成果，三格式同源。几何规则合格不等于消防、结构或工艺审查通过。

每次代码发布至少做目标项目测试、受影响合同回归和现有仓库 CI；共享合同变动要求三路消费测试，UI 改动追加浏览器测试，模型改动追加实机记录。测试失败不能用“暂时删除用例”过关。

## 10. 模型实验和 16GB 机器怎么排队

开发可三路并行，但同一台 Mac 的三个大模型不并行加载。`coordination.json` 记录设备 lease 与队列；真实 worker 仍需本机单实例/进程互斥，不能把 JSON 文件当内存调度器。暂未部署 worker 时由同一操作者串行执行，先确认前任务结束和模型卸载，再交出设备。

T0 确定性基线、T1 首个 16GB 本机候选、T2 条件升级、T3 另行授权的大本地硬件参照。按任务角色分赛道，LLM、VLM、生成、重绘不合并排名；既有模型候选以 `docs/MODEL_REQUIREMENTS_M4_16GB.md` 和 benchmarks 登记为准，本轮不重新选型。

每次实验保存 run_id、case/revision、输入/权重/配置 hash、量化/后端/节点版本、seed、raw/final、各阶段耗时、资源口径、失败/人工修正、审查。重复失败也进统计分母；未知指标为空，不填 0。同一数值 seed 不代表不同模型同样随机输入。

出现 OOM/超时：保存失败，释放资源，降尺寸或换模型须新配置/attempt；不静默改参数、关内存保护或转云。三项目可顺序复用权重，不下载三份。BIMFACE 外发需另行授权；会员身份不证明格式/API已联调。

## 11. 每次总控回顾只看六个问题

1. 三条线现在各在做哪个任务、谁负责、基于哪个 main？
2. 本轮可运行和已验证的东西是什么，证据在哪里？
3. 是否改共享接口、影响其他楼层或使下游数据过期？
4. 阻塞是什么，由谁处理、满足什么条件才解除？
5. 下一项最小验收是什么，需不需要占用本机模型资源？
6. 当前有哪些版本等待工程评审、用户验收或发布？

更新触发点：开工、切片完成、接口提出/决定、出现阻塞、实验结束、发布/失败、会话结束；长会话按登记的 next_checkpoint 回报。不要求为了好看固定日报，也不承诺无人触发时自动巡检。

进度不用“P1 80%”这类估计；按每个维度的已验收切片、阻塞年龄、待评审条数、接口回归和实验接受率来观察。快照注明提交和时间，不能当实时查询。

## 12. 本轮落地和三路启动方式

本轮新增管理规程、协调登记空表、开工/交接和合同/联调模板、三个项目局部 AGENTS；根 README/AGENTS 增加导航。**不修改原 backlog 状态、不把任何人登记为已开工、不运行模型、不清空代码、不改 baseline/vendor/合同。**

每条新开发会话可使用：

```text
请在 yuancustom/AutoPlanDesign 开发 P{1/2/3}。
先读取 main、根 AGENTS.md、CONTROL.md、governance/PARALLEL_CONTROL.md、
任务/交付/协调台账，以及对应项目 AGENTS.md 和 README。
提交开工卡，声明 task_id、base_sha、允许路径、验收与依赖；
获得总控认领确认后，只完成一个可运行切片。
共享接口先提案，发布进入 main 串行队列；结束留下 handoff，
分别报告文档、原型、实现、模型实测、用户验收，禁止自批。
```

建议首批 P1-01、P2-01；P3 提出输入准备子任务、保留父阻塞。总控先处理 GOV-01 和 BENCH-01 的公共基础。代码/原型不可代替实际模型效果评估；最终合并的是经过合同验证的能力，不是再合并三套耦合源码。
